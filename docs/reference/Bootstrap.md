# First Login Knowledge

`Bootstrapper.bootstrap()` runs when the operator command is `play` after `logon`. It learns only from text the game server sends. The logged-on character is the one named in `logon`, and that name must be one returned for the connected account.

`CommandChannel` answers these gates before treating a reply as finished:

- `Do you wish to connect anyway (Y/N)?` and `Please type Y or N?` get `telnet.replace_existing` from `resources/agent.yml`. `Y` takes the existing link. `N` stops the session.
- `That character is being saved. Please reconnect in a moment.` stops the session.
- `Authentication failed.`, `Invalid authentication message.`, and a site ban stop the session. The server sends these as `ERROR: ` lines.
- `[Hit Enter to continue]` is acknowledged with an empty line and is left out of the stored text.

A normal reply ends on a playing prompt such as `<20hp 100m 100mv>`. The next command is sent only after that prompt. An idle timeout with no prompt raises `PromptTimeout`.

1. Drain the login burst until the playing prompt. Keep those lines as local session evidence and on the legacy `WorldKnowledge.login_lines` view.
2. Send `commands`. Observe those names, in that order, as the session availability list. Store their learned descriptions on WorldKnowledge. For each name, send `help <name>` and store a `HelpTopic`. `learn_categories` runs before that list: it sends bare `help`, asks the `categories` prompt to read the two-column index, and stores each command's category on WorldKnowledge without granting availability. A category already stored is left in place. `learn_commands` then observes the `commands` list without clearing those categories. `learn_help` sends `help <name>` for each command in that list, and also for a command the help index stored that the list omitted, such as `!`. When the command already has a category, the `help` prompt is sent unchanged. When it does not, that request also asks for one category chosen from the names already stored. The raw server page is retained first. Model topics stay on the lesson, the attributed enrichment evidence, the stored HelpTopic, and the command description. A page with no help still receives a category. When `bootstrap.defer` is false, the `categories`, `commands`, and `help` prompts are loaded, and an Ollama client is present, `bootstrap()` runs these three steps in that order before `areas`. A help page that lists many commands, such as `socials`, keeps each extracted topic. Without those prompts, or when `bootstrap.defer` is true, `bootstrap()` does not call Ollama. It sends `commands` and `help <name>` and stores the server text without a category. `bootstrap.defer` in `resources/agent.yml` defaults to false. In both modes, command descriptions belong to WorldKnowledge and are included in the final knowledge document. Look-prompt items remain in live room memory. Set `bootstrap.defer` to true to skip every Ollama request, store the server help on `WorldKnowledge`, and persist that document. The login report counts help pages, extracted topics, commands, and how many commands have a category.
3. Send `areas` and store `AreaRecord` entries from the two-column, 39-character layout (`[level] author: name`).
4. Send `who` and store `PlayerRecord` entries. A player is `agentic` when the character name matches an agent document. The logged-in character is `self_character`.
5. Send `look`. Store the room, exits, and item lines. When `bootstrap.defer` is false, that look reply is the user text of the `look`, `items`, `exits`, and `mobs` prompts. A stored sample in `user` is not sent. The `look` prompt's items are stored on the session room. A sentence such as `There is a sign on the wall.` is an item named `sign` with `source` `description`. A four-space line is `source` `object`. `play.MemoryObservation.apply_room_observation` applies the parsed room directly to live memory, preserving separate provisional IDs for duplicate sightings before the legacy snapshot is built. The runtime no longer reimports that snapshot through `absorb_world`; later play reads the live observation directly. Legacy memory saving does not persist the richer session evidence queue. Classify people in the room:
   - a name that matches `who` is a player, and the record gains `room_name`
   - a proper name that is not in `who` is an NPC
   - an article-led description (`a`, `an`, `the`, `some`) is a mobile

When `bootstrap.defer` is true, bootstrap does not call Ollama. It stores the server command list and each server help page on `WorldKnowledge` and saves that document. Each stored command is `name`, `category`, and `helpText`, in the order the server listed `commands`. A blank help text is filled from the matching `HelpTopic`. New categories stay blank; existing learned categories are retained. The areas, who, and look snapshot is saved again afterward and still includes those commands. The room prompts are not sent. When `bootstrap.defer` is false, Ollama runs and command descriptions stay on WorldKnowledge through its shared legacy memory view. The final knowledge snapshot includes those descriptions. The command-checkpoint callback runs after all command help pages in either mode. A model failure keeps the server help fallback. Server text from `areas`, `who`, and `look` is saved in both modes. `learn_categories`, `learn_commands`, and `learn_help` still call Ollama when they are invoked directly with defer left false.

When `bootstrap.initial` is true in `resources/agent.yml`, process startup connects the saved account for the agent's `accountName`, logs on `characterName`, and runs this bootstrap before the control loop. The mode stays idle. A missing saved connection, or a character the login did not return, is reported and bootstrap does not run. The control loop still starts.

The first `play` after logon runs bootstrap when the character has no stored commands. A later `play`, including the next time the process starts, loads world knowledge. When that document has a command list, or help topics from a document saved before commands were stored, the runtime restores descriptions and performs one fresh `commands` exchange before creating the engine; the full help bootstrap does not run. Help topics never become available verbs merely by being loaded. The stored room and players are left out of the session. A missing document, or one with neither commands nor help topics, runs bootstrap. A failed knowledge load is reported and does not bootstrap. The control command `bootstrap` runs bootstrap again after logon, including when commands are already stored.

`CommandChannel` uses the telnet client and does not open its own socket. Later play decisions read `WorldKnowledge`. They do not scrape the telnet client directly.

Look-prompt item enrichment is accepted only for the captured room ID and observation revision. Newer looks or visits invalidate a delayed result. Model room names and exits cannot overwrite the server observation. Duplicate raw objects remain distinct even if a model lists fewer of them. These IDs are local runtime records; the legacy knowledge document still has its original snapshot shape.

Availability is granted only by the parsed server command list, not the categories/help index or model responses. Its observed names precede retained historical/index-only descriptions in the knowledge catalog. Refresh can revoke names while preserving help. Metadata updates use the common immutable KnownCommand and ordered CommandList rules.

## Evidence and completion

`ObservationPipeline` folds bootstrap, restored-login verification, and gameplay responses into WorkingMemory and the local WorldKnowledge view. It records immutable raw responses before parsing and creates ordered semantic evidence with source references. Login text and raw responses are local provenance. Commands/help, listed areas, the who roster, and room observations are eligible for later KM mapping. Listed areas do not establish exploration, and who does not establish room presence. Help examples cannot become a live room or fight. Model output has its own sequence and references the server observation; only applied enrichment is eligible for handoff. Failed, malformed, or stale model output remains local for review.

`session.bootstrap` records the current attempt, stage outcomes, exact required evidence IDs, selected player name, marker-reset result, and any error. Collection requires a login prompt, a nonempty parsed command list, nonblank returned help pages, parsed area and player entries, and a look with its title and exits section. A missing section leaves `incomplete`; a complete collection becomes `awaiting_acceptance`. Negative help pages are evidence too. A partial or timed-out response is retained without applying it as a complete page. Optional model failures do not block raw collection. Partial legacy room snapshots do not authorize current presence or item enrichment.

When a player is supplied, an attempt resets `som-bootstrap` to `f` with replacement semantics. A reset failure is reported and local collection continues. `BootstrapCompletion.publish` can assert `t` only for that attempt's player after all required eligible records have been explicitly acknowledged; it checks KM reasoning errors and retries a failed reset before completion. Local snapshot saves and the existing command-only KM assertions do not acknowledge this evidence. Step 6 provides typed [mapping plans](KmEvidence.md); step 7 supplies the transfer lifecycle. Roster and other unsupported records still prevent full acceptance, so normal collection currently remains `awaiting_acceptance`. Local provenance is outside the KM acknowledgment range. Acceptance is not durable KM saving.

Initial and forced bootstrap use this same path. Forced bootstrap requests a new prompt with an empty line when the prior prompt was already consumed. A new attempt retains the journal history but requires its own evidence, and resets the completion marker. The engine reuses the synchronized bootstrap channel and its last prompt, without granting current-room authority from a saved snapshot. The journal's random stream ID orders local evidence; full authenticated session/connection identity enforcement remains later integration work.
