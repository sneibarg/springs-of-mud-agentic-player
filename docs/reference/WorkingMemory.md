# Working Memory

`WorkingMemory` lasts for one play session. `clear` drops it. Do not add the session sections to `WorldKnowledge.to_document`. Command descriptions use the shared knowledge view described below; current command availability stays on the live session.

- `remember_player`, `remember_mobile`, and `remember_npc` retain historical session records. Live presence comes from `current_beings()`, not the accumulated lists. These helpers accept `being_id` and `room_id`; name-only updates require an unambiguous name. Agentic players are players with `agentic` set. Each being keeps an `auras` list. Look prefixes that end in `Aura`, such as `(White Aura)`, are stored by the label. A later look replaces that list. Remembering the being again without an aura list leaves the stored auras in place. `(Invis)`, `(Wizi)`, and the other non-aura prefixes are not stored.
- `observe_commands(names)` replaces current availability from a complete server `commands` response, preserving server order. `remember_command` and `replace_commands` update descriptions only. Blank category/help updates preserve learned values. Historical metadata and help cannot grant availability, and replacing descriptions cannot revoke it. Every new login verifies availability from the server even when descriptions are restored.
- `remember_room` keeps each room seen this session: name, description, exits, and items. An item is `name`, `line`, and `source`. `name` is the word used with `look`. `source` is `object` for a four-space line and `description` for a sentence such as `There is a sign on the wall.` A later look that passes items replaces that list. Omitting items leaves them stored. Omitting description, exits, or items leaves the stored value in place. Explicit empty strings and lists replace it. Each room has a `room_id`; use it to update or retrieve a room when titles repeat. After the memory document is saved, later play reads these items instead of asking the model again.
- `CommandCategorizer` is the later categorization phase. It fills `{command}` and `{help}` on a prompt and sends that body through `OllamaClient`. First login does not call it, and no command-category prompt is in `SOMDB.Prompts` yet.
- `remember_consider` stores one `ConsiderOpponent`. The survival lines are the seven strings from `springs-of-mud-server` `Info.do_consider`. `outlook` is `safe`, `even`, `risky`, or `fatal`. A refusal such as `They're not here.` stays stored with `outlook` `unknown`.
- `remember_conversation` stores one `Conversation`: topic, participants, a location of `channel`, `tells`, or `room`, the location name, and the agent's `interest` priority. The same topic, location, and location name stay one conversation. A later call with participants replaces that list. Omitting interest leaves the stored priority. `set_interest` changes it. A higher integer is a higher priority. `conversations` lists the highest interest first.
- `note_aggressive` and `play.MemoryObservation.observe_line(memory, line)` for a room line ending in `is here, fighting YOU!` mark a mobile aggressive. Seeing that mobile again without aggression evidence does not clear the flag. Explicit `aggressive=False` clears it, and unknown aggression is `None`.
- `play.MemoryObservation.apply_room_observation` applies parsed bootstrap/gameplay looks directly, before the legacy WorldKnowledge dictionaries can collapse duplicate labels. `absorb_world(memory, knowledge)` remains the compatibility importer for legacy snapshot facts and seeds an empty visit only; it cannot overwrite an already observed live look. It preserves current items and considers. WorkingMemory imports no play parser or world-knowledge type.
- `write_review(path)` writes `to_review()` as indented JSON: live session state, players, agentic players, mobiles, npcs, aggressive mobiles, rooms, commands, considered opponents, and conversations, plus room-exit history, item history, and encounter-to-consider references. The same consider stored under a target and a subject is written once.
- `write_collection(agent_name)` upserts the legacy sections of that snapshot into `resources/collections/SOMDB.Memories.json`. The document's `agentName` is the lookup field. A later dump for the same agent, ignoring case, replaces that document and leaves other agents in place. Pass a path to write a different collection file. The `memory` command still writes the review file and does not call this dump.
- `from_collection` restores a memory document through the `remember_*` methods. It ignores `savedAt` and `id`. A blank `agentName` raises. The runtime loads the live snapshot with `GET /api/v1/agent-memory/{agentName}`. A `404` leaves the session empty. After play, the runtime saves the current `to_collection` with `PUT` on that path. An idle exit that never played leaves the stored document in place. `write_collection` remains the fixture writer.

## Live play state

`WorkingMemory.session` is a `PlaySession` dataclass. GameplayEngine reads and updates that same session rather than keeping its own mutable play state. Recreating the engine with the same WorkingMemory preserves the current room, progress, combat, and retry-suppression markers. A constructor's `room_current` hint seeds an empty visit only; it cannot overwrite an existing visit with an older WorldKnowledge snapshot. Fresh bootstrap observations update the visit through the play adapter.

- `session.progress` is `memory.PlayClock`: score counters, level, experience, score-page hours, notch, cooldown, saves, and score cadence. Its `note_score` maintains first-score and level-change baselines.
- `session.room` is `RoomVisit`: current room name/exits, whether the room is current, tried exits, and fresh consider IDs. It also holds room/visit IDs, current occupant IDs, a room-observation revision, presence completeness, and pending movement context. `observe`, `depart`, and `note_consider` maintain those markers. Room identity is explicit; a new provisional visit clears previous occupants and freshness even when its title is identical.
- `session.combat` is `CombatState`: hit/max-hit, position, fighting, engaged encounter IDs, and uninvited threat IDs. Ambiguous partial fight lines set an unidentified-threat marker without choosing a mobile. An observed standing score or confirmed flee clears the fight and threat markers. A failed flee retains them.
- `session.pending_action` is a `PendingAction` recorded before an exchange. A successful response is folded before the pending action is removed. On interruption it remains visible, including whether the response returned. Recreating the engine does not resend it; the engine continues to drain observations but waits for later recovery work or an explicit memory reset.
- `session.last_prompt` preserves the latest playing prompt when a channel is recreated. The danger rule can still read its hit points.
- `look_unread`, `score_unread`, and `areas_unread` preserve the existing unusable-reply markers across engine recreation.

`to_review` includes these records under `session`, with sorted arrays for sets and ordinary JSON values. `PlaySession.from_json` normalizes camelCase fields and reconstructs the component records for local callers. It is not a checkpoint restore workflow or permission to trust an old session.

`to_collection` deliberately omits `session`, and `from_collection` starts with a fresh PlaySession even if an unsupported session field is supplied. The existing modulith memory schema cannot retain this state. Durable checkpoints and identity validation remain later steps; no new live-state persistence is claimed here. `clear` replaces the live session and clears every legacy section. Engines read the replacement through WorkingMemory rather than retaining stale aliases.

## Observation replacement and identity

`SessionBeing`, `SessionRoom`, `SessionItem`, and `RoomExit` are dataclasses in their own files with `from_json` boundaries. IDs are generated independently of labels. `being_by_id`, `room_by_id`, `item_by_id`, and `exit_by_id` retrieve those records. Name lookups return a value only when unambiguous; plural name lookups return all matches. Name-only mutation raises on ambiguity.

The telnet look contract supplies no authoritative room or encounter IDs. Live records are therefore marked provisional. An uninterrupted, unique sighting in the same visit can retain its ID; disappearance, a new visit, or duplicate indistinguishable rows creates separate provisional encounters. Identical names never merge separate visits. Backtracking does not automatically recognize an old room from its title. Durable ID recovery and explicit reconciliation remain later work.

A complete look has a room title and the `Obvious exits:` section, framed by the channel's prompt. It replaces current occupants, exits, and raw object sightings. An explicit empty section clears current membership. Historical beings, rooms, removed exits, items, and encounter considers remain available by ID. A partial parsed look can add observations but cannot clear an omitted section. A changed aura or fighting observation invalidates that encounter's consider freshness. Old name-based considers cannot supply a current encounter's outlook. An explicit consider response of `They're not here.` removes that target from current presence while retaining its encounter history. A failed look makes old presence unavailable for tactical decisions until another valid look.

Mobiles offered to KM come only from current occupant IDs. Ambiguous `kill` and `consider` targets are not sent; this runtime does not invent numbered target syntax. Known players remain players when they attack, including on partial fighting-you lines. Unknown classifications are not accepted as combat targets.

Directed exits have their own IDs, a last confirmed destination and destination history, and nullable open/unlock requirements. A directional reply containing a complete room observation establishes only the observed forward connection. Recognized refusals retain the origin and mark the direction tried. Other replies without a complete destination observation are treated as uncertain. An uncertain reply invalidates current location; a later look gets a provisional location but does not establish that the earlier move succeeded. Reverse connections, door feasibility, and successful arrival are never inferred from sending a command. A closed-door refusal records the observed open requirement; absent lock evidence stays unknown.

Items with duplicate labels remain separate sightings. Raw object lines have `keyword_known=False`; their display text is not a confirmed look keyword. Model enrichment is tied to the source room ID and revision. A delayed result is rejected after a newer look or visit. Unique line-backed enrichment retains the item ID and keyword on later matching looks, while incomplete model output cannot collapse observed duplicate objects. Item IDs and historical room associations do not establish ownership, equipment, or permission to acquire an item.

`CommandChannel.drain` exposes prompt-delimited frames alongside its existing flat line result. Recognizable unfinished room pages are buffered in `session.observation_lines`, survive engine recreation, and cannot trigger destructive replacement before their prompt. Multiple queued looks are applied in prompt order. Unprompted non-room messages are still observed without stalling gameplay. A header fragment without its room title invalidates the location for a fresh look rather than becoming a new room name.

The operator review includes IDs and the added history sections. The legacy REST body strips identity metadata and omits `session`, `room_exits`, `items` history, and `encounter_considers`; room item lists retain their old supported shape. Legacy restores can preserve duplicate rows as separate historical records, but cannot recover their original IDs or richer nullable flags. They never become current occupants or fresh considers. Companion persistence schema changes and full session identity enforcement remain outside this step.

## Command knowledge and availability

`KnownCommand` is the single immutable command value: name, category, and help text. `from_json` normalizes camelCase at the boundary, and construction normalizes names and rejects blanks. `CommandList` is the single ordered unique collection implementation. Remembering a duplicate keeps its insertion position and preserves previous fields when the incoming field is blank. Replacement validates the full input before changing the collection. Merge keeps primary order and nonblank metadata, fills gaps from fallback descriptions, then appends fallback-only names.

`WorldKnowledge.commands` owns learned descriptions. `command_records()` exposes explicit rows only. `WorkingMemory.command_knowledge` is a compatibility view of the same collection during bootstrap/restoration; before binding, it holds historical metadata loaded from the memory API. Binding uses the existing precedence: nonblank memory metadata wins, knowledge fills blanks. Actual bootstrap learning and CommandCategorizer write WorldKnowledge. Shared values are immutable; there is no separate mutable SessionCommand/CommandRecord/LearnedCommand model.

`WorkingMemory.commands()` and `command_named()` remain description-view APIs for review, legacy serialization, and existing callers. They are not executable-command lookups. Clearing WorkingMemory detaches this view without deleting the engine's separate WorldKnowledge object.

`session.available_commands` is a separate CommandList containing names only, in the latest server-list order. `session.commands_observed` distinguishes unknown availability from a processed response with no usable verbs. `session.command_available(name)` requires both observed state and membership. Refresh can remove one or all verbs without erasing their descriptions; help-index rows, model categories, and memory/knowledge restores do not add permission.

The operator review exposes available names and observation status under `session`; its top-level commands remain learned descriptions, including unavailable historical entries. The legacy memory body keeps its old command shape and omits availability. Restoring that body always starts with unknown availability. The local PlaySession `from_json` boundary supports its review shape and rejects non-boolean observation flags; full trusted checkpoint restoration remains later work.

`CommandSituation.available_commands` projects merged descriptions onto observed availability only. It uses public collection APIs, preserves observed order and metadata precedence, and excludes help synthesis and unavailable knowledge-only names. Publishing an observed empty list replaces the retained KM index with an empty sequence. Unknown availability publishes nothing. Later publications use replacement semantics for metadata and membership. Historical command frames can remain in KM, but neither their existence nor a stale decision bypasses the engine's current availability and prohibited-command checks.

## Session evidence and bootstrap progress

`PlaySession.evidence` owns an EvidenceJournal of immutable SessionEvidence snapshots. A lazily allocated stream ID and monotonically increasing sequence identify records independently of timestamps. UTC observation times, source type, origin (`bootstrap`, `restore`, or `gameplay`), command, raw lines, and source IDs preserve provenance. Payload reads return detached JSON values, so later room replacement or model enrichment cannot rewrite an earlier observation. Bootstrap and the recreated engine append to the same queue.

`pending()` selects unacknowledged eligible records. Raw responses, login text, help-index source pages, and unapplied model results remain local provenance outside this selection. `acknowledge` is explicit, atomic for its selected IDs, and rejects local-only or foreign records. It is a boundary for the future mapping adapter, not a claim that an HTTP snapshot save transferred facts to KM. No production code acknowledges full evidence in this step. Model enrichment retains its source room ID/revision where applicable. Room, score, consider, command, roster, area, and general gameplay observations share the play adapter.

`PlaySession.bootstrap` owns BootstrapProgress: collection attempt ID, stage outcomes, required eligible evidence IDs, player name, status, marker-reset result, and error. Completed local collection awaits acceptance. An interrupted or missing required page remains incomplete even when other evidence was accepted. Forced collection creates a new attempt without erasing older evidence or reusing its acknowledgments. BootstrapCompletion publishes the completion marker only after the required acceptance set succeeds for the selected player.

Session review includes the journal and progress and supports local JSON round trips. The legacy memory and knowledge REST bodies omit these sections; their schemas and fixtures are unchanged. Legacy restoration creates a fresh journal and progress. These stream/attempt IDs are not an authenticated login envelope or a durable checkpoint. Full identity binding, bounded retention/periodic retries, and persistence remain later steps.

[KmEvidenceAdapter](KmEvidence.md) now plans supported mappings from the immutable journal prefix, including captured command metadata, movement-origin edge updates, current beings, and fresh considers. Plans do not acknowledge the journal; partial and unsupported records remain pending. Explicit gear contracts exist for future producers, without treating raw room items as possessions or acquisition permission.
